## 1. Deleting a viewed experience no longer fails (§1.1)

`experience_views`' foreign key to `experiences` doesn't cascade (deliberately, per V10), and
`ExperienceService#deleteExperience` cleaned up rounds, proof documents, review logs, and edit
snapshots — but not views. Any experience someone signed-in had ever opened couldn't be deleted:
the delete hit the constraint and `ApiExceptionHandler` turned it into an opaque
`409 "That operation conflicts with existing data"`.

The path that made this reachable: a **free contribution** or **reference submission** has no
entitlement (nothing to buy) and no payout row (`approve()` skips those for free submissions), so
neither existing guard stopped it. Publish → someone views it → unpublish → delete → 409.

- `ExperienceViewRepository.deleteByExperienceId` added, called from `deleteExperience` alongside
  the other four cleanups.
- Chose the explicit delete over adding `ON DELETE CASCADE` so the cleanup stays visible next to
  the others rather than being implicit in the schema — and so it needs no migration.
- Tests: a regression test using exactly the free-contribution path above, plus an added
  assertion on the existing cascade test.

**To check locally:** create a free contribution, publish it, open it from another signed-in
account, unpublish it, delete it. It should just delete.

## 2. View counting can't 409 a page load any more (§1.2)

`getPublicView` incremented `viewCount` by mutating the entity and saving it. `experiences`
carries an optimistic-lock `@Version`, so **two different viewers' first views landing at the same
time** collided and one of them got a `409 "This resource was updated by someone else"` on what
was, from their side, an ordinary page load. `recordView`'s `ON CONFLICT DO NOTHING` de-dupes the
same viewer; it does nothing for two different ones.

- `ExperienceRepository.incrementViewCount(id)` — a native `UPDATE experiences SET view_count =
  view_count + 1`, which is atomic and deliberately leaves `version` alone. A view isn't a content
  edit, and letting it invalidate a concurrent editor's in-flight update would cost more than the
  lost-update protection buys on an append-only counter.
- `clearAutomatically = true` on the query, and `getPublicView` re-reads the experience afterwards
  so the viewer's own view shows up in the response they get back.
- `Experience.incrementViewCount()` deleted (nothing calls it now), and `view_count` is mapped
  `updatable = false` so no future `save()` of a stale entity can write an old count back.
- Stale comments fixed in passing: `Experience.viewCount`, `ExperienceTeaserResponse.viewCount`,
  and `shared/types.ts` all still described a raw per-page-load hit counter, which V10 changed to
  one-per-viewer months ago. (`V9`/`V10`'s own SQL comments say the same thing but are left alone
  — editing an applied migration changes its Flyway checksum.)

**To check locally:** open a published experience from two different signed-in accounts at
roughly the same time; both should load, and the count should read 2.

## 3. Rate limiting keys on the real client behind a proxy (§1.3)

`RateLimitingFilter` bucketed on `getRemoteAddr()`, which behind Railway's edge is the proxy for
every request. The per-IP auth limits were therefore effectively global: **10 logins per minute
across the entire user base**, not per person. The original code's reasoning for not trusting
`X-Forwarded-For` was sound for a directly-exposed app — the header is attacker-controlled there —
but stopped matching reality the moment this deployed behind a proxy.

- New flag `app.rate-limit.trust-forwarded-for` (env `TRUST_FORWARDED_FOR`), **default false**.
  False keeps today's local-dev/direct-exposure behaviour exactly. True keys on the left-most
  `X-Forwarded-For` hop, falling back to `getRemoteAddr()` when the header is missing so a request
  that bypasses the proxy is still limited rather than sailing through on an empty key.
- Wired through `SecurityConfig`, which already constructs the filter by hand.
- New `RateLimitingFilterTest` covers both settings, including the two failure modes that matter:
  a spoofed header is ignored when the flag is off, and two clients behind one proxy get separate
  buckets when it's on.

**Action required on deploy:** set `TRUST_FORWARDED_FOR=true` on the Railway `api` service. The
fix does nothing until that's set. See `06-deployment.md`.

## 4. Round types read as labels everywhere (§1.4)

The detail page rendered `round.roundType` raw, so a contributor picked "System design" from a
dropdown and the viewer who paid ₹99 saw `SYSTEM_DESIGN`. The label map existed but was private to
`SubmissionWorkspace.tsx`.

- `ROUND_TYPES` / `roundTypeLabel` moved to `web/src/lib/roundTypes.ts`, used by the submission
  workspace, the detail page, and the admin review queue.
- Falls back to the raw value for anything unrecognised — `round_type` is a free-form column
  server-side, so an older row still renders.

## 5. Admins can read what they're approving (§1.5)

The review queue showed company, role, teaser, proof links, and `"1 round(s), 1 proof
document(s)"` — the rounds themselves were never rendered. The questions, approach and
interviewer notes, i.e. the entire thing being verified and paid for, weren't on screen at the
moment the admin clicked "Approve & publish". (`05-capabilities.md` claimed otherwise; corrected.)

- Full round content now renders in each queue card, same shape as the viewer's detail page.
- New `ReviewFacts` block: level, location/remote, interview date, outcome, difficulty, timeline,
  compensation, prep advice, and the price it'll publish at. All of it was already in the payload.
- Empty rounds or proof documents get an explicit warning line rather than rendering nothing —
  either state means something is off, since neither is submittable through the normal path.
- **Approve & publish now asks for confirmation.** It does four things at once (publish, stamp
  `publishedAt`, log the review, create a payout liability) with no one-click undo, while a
  contributor deleting their own draft already had a modal. The dialog spells out what will
  happen, and says explicitly when no payout will be created (free reference submissions).
- `ConfirmDialog` gained a `tone` prop so a constructive-but-consequential action isn't styled as
  a destructive one. Default stays `"danger"`, so every existing use is unchanged.
- The queue's two free-text inputs got `aria-label`s (they had placeholders only).

## 6. Password reset is reachable (§1.6)

`POST /auth/forgot-password` and `/auth/reset-password` have been implemented, rate-limited and
token-hashed since Phase 2, with **no way to reach them from the app** — no link, no screen, no
route. A user who forgot their password was locked out permanently, independent of the missing
email provider.

- `web/src/components/PasswordReset.tsx` — two screens: request a link, and set a new password
  from a `?token=` link.
- `/forgot-password` and `/reset-password` routes; "Forgot your password?" on the login tab only.
- `router.tsx` now exposes `search` (the query string) — it only tracked `pathname`, and the reset
  link's token lives in a query param. Also fixed: the first-mount `replaceState` dropped the
  query string, which would have eaten the token on the very load that needs it.
- `api.forgotPassword` / `api.resetPassword`; `MessageResponse` added to `shared/types.ts` (the
  request types were already there).
- The confirmation copy says "if an account exists", never "we've emailed you" — it mustn't leak
  whether an address is registered, and no email is actually sent yet.
- Password confirmation is checked client-side before the call, because the token is single-use:
  a typo in a field you can't read back would otherwise set a password you don't know, with no
  second attempt.
- **`AuthService#forgotPassword` now logs a complete link** (`{web-base-url}/reset-password?token=…`)
  rather than a bare token, since until there's an email provider an operator has to read this out
  of the logs and hand it over. New `app.web-base-url` config (env `WEB_BASE_URL`), defaulting to
  the Vite dev server.

**Still open, deliberately:** no email is sent, and a reset doesn't revoke that user's existing
refresh tokens — see "Not done" below.

## 7. Pagination params are bounded (§1.7)

`size` was clamped upward only; `page` wasn't clamped at all. `?page=-1` threw
`IllegalArgumentException` out of `PageRequest.of` and came back as a `500`. Both bounds are now
clamped rather than rejected — the same forgiving posture `resolveSort()` already takes toward an
unrecognised sort value, so a stale bookmark degrades instead of erroring.

## 8. Deleted `web/src/components/SubmissionWorkspace/` (§2.1)

1,179 lines across 8 files that were never bundled: Node/Vite/TypeScript resolution prefers
`SubmissionWorkspace.tsx` over the sibling directory, confirmed with `tsc --traceResolution`. An

Removed the directory, per your call, keeping the working monolith. Note that this leaves

upload, edit history, delete confirmations and autosave — the refactor is still worth doing, just
as a deliberate piece of work rather than a half-landed one.

## Not done (flagged, not fixed)

- **Password reset doesn't revoke existing sessions.** `resetPassword` changes the hash but leaves
  every `refresh:<jti>` key in Redis alive, so a user resetting *because* they think they're
  compromised stays compromised for up to 30 days. This is §4 of the review, not one of the seven,
  so it's left alone — but it's a small change (a per-user refresh-token index, then delete on
  reset) and it belongs with the reset work whenever that's picked up.
- Everything else in §3–§6 of the review: notifications, free experiences in My Library, admin
  moderation surface, the write-only review log, refunds, the responsive/accessibility pass, and
  the `04-handoff.md` / `05-capabilities.md` changelog reconciliation.
